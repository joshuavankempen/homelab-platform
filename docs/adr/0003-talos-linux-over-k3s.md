# ADR-0003 — Talos Linux as the Kubernetes OS

- **Status:** Accepted
- **Decided:** 2026-08-16
- **Recorded:** 2026-08-20

## Context

Kubernetes runs as VMs on Proxmox ([ADR-0001](0001-proxmox-and-clean-install.md)):
one control-plane-plus-worker on `pve-lenovo`, one worker on `pve-hp`. That
leaves the choice of what operating system those VMs run.

This repository's premise is that the estate is defined in Git and reconciled by
machines. A node configured by SSH-ing in and running commands is the one part of
the stack that would not be — and would quietly become the place where
undocumented state accumulates, which is exactly the problem
[ADR-0001](0001-proxmox-and-clean-install.md) exists to escape.

There is also a stated learning objective: to come out of this genuinely
understanding the Kubernetes control plane, not merely able to run `kubectl`.

## Decision

**Talos Linux.** Machine configurations are generated by `talhelper` from a
committed `talconfig.yaml`, with secrets kept out of the repository. k3s on
Debian stays documented as the fallback if Talos proves unworkable.

## Options considered

| Option              | Why it was plausible                                                                                                     | Why it lost                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Talos Linux**     | Immutable, API-driven, no SSH and no package manager: the node is a declarative artifact like everything else in the repo  | **Chosen.** Upgrades are an image swap with rollback, and the attack surface is minimal because there is almost nothing on disk to attack.                                           |
| k3s on Debian       | Fastest path to a working cluster; a normal Linux box underneath when something breaks; every tutorial assumes it          | The "normal Linux box" is the problem — mutable state outside Git, and the debugging convenience is the same convenience that lets configuration drift in unrecorded.                 |
| kubeadm on Debian   | The reference implementation; closest to what certifications and many jobs actually use                                    | All of k3s's drift problem plus considerably more assembly. The learning it forces is real, but front-loaded onto the one layer that must work before anything else can be built.     |

## Consequences

- **Debugging is `talosctl`, not `ssh`.** There is no shell on the node. This is
  the largest day-to-day cost and a genuine learning curve — worth naming here
  rather than discovering during an incident.
- **Every node change is a machine-config change.** Slower per change, but the
  node's state is reviewable as a diff and reproducible on a rebuild.
- **Some Helm charts assume a conventional distribution.** Anything wanting
  hostPath mounts, kernel modules or host packages needs a Talos system
  extension declared in the image. Expect this with storage and monitoring
  components specifically.
- **`talhelper` becomes a dependency of cluster recovery.** The rendered configs
  are gitignored because they contain the cluster CA, so a rebuild depends on the
  tool plus the encrypted secrets file. Losing that secrets file means rebuilding
  the cluster from scratch — it belongs in the password manager, not only on
  disk.
